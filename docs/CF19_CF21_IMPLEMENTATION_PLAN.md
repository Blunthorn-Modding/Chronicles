# CF19–CF21: roles, departures and paired area changes

26 October 2026. New requested scope after accepted dev54. Branch `design/core-roles-departures-transitions`. This is an implementation contract and UI review package; Minecraft code, deployed worlds and the dev54 pack remain unchanged in this design pass. The organizer's standing UI workflow requires a dedicated design pass and lead review before implementation. The paired [UI design](CF19_CF21_UI_DESIGN.md) and [mockup](design/roles-departures-transitions.html) provide that review surface.

## Confirmed requirements

- **CF19, Player roles:** Core owns reusable definitions, selection/assignment, limits, starting and respawn locations, starting gear and private named-book entitlements. Roles support unique characters and shared backgrounds through a configurable limit. Quiet Below supplies its default definitions in YAML. Operators can create/edit definitions in the editor.
- **CF20, Departure points:** an exact bound block and an existing boarding region define an interaction. Quiet Below's only ship is single use. The actor receives two separately worded, stacked confirmations. Final acceptance takes all **online participants physically aboard**; offline characters are not selected from saved positions. Departed characters become **Spectators**, and participation cannot be restored by ordinary join, role selection or reconnect. If every remaining enrolled participant leaves, the **campaign** ends, not merely this meeting's play window.
- **CF21, Area changes:** one area owns one set of bounds and independently saved Start/End states. Create it by choosing which state exists first, selecting two corners in-world with a debug shovel or existing position commands, then explicitly saving. Recapture either state later, apply a saved state, or delete with a choice of Start, End or no world change. Include supported block entities and container contents; overwritten target contents are intentionally discarded. Do not copy players, entities or Chronicle transaction identities. Ship removal and sinkhole appearance are uses of this general tool.

No session-number timetable is implied. A sinkhole can be deliberately triggered during play or attached to an optional configured condition; there is no new mandatory “session one” event. The organizer still builds the map. Existing research-journal prose and story events remain frozen for the final content pass.

## CF19 — player roles

### Definition and configuration

Proposed authoritative file: `config/chronicle/player-roles.yaml`. Each campaign may register a bundled YAML resource, initially `data/quiet_below/chronicle/player-roles.yaml`. On first creation, materialize registered defaults; thereafter preserve the operator's file. Default upgrades must not overwrite edited roles, restore deleted roles or create assignments. Importing additional defaults is an explicit future/admin operation, not a silent reload effect.

The normalized definition contains stable ID, display name, public description, selectable versus GM-only state, capacity, optional revision-pinned starting/respawn Points, starting item definitions and named-book IDs. No raw world coordinates are required in the campaign's defaults. Point references are chosen in the editor against the current map; missing/stale points are shown as unresolved, never silently rebound. Blank points preserve the corresponding vanilla behavior.

The editor and YAML operate on the same validated catalog. Save by expected revision/fingerprint with an exact previous-file backup and atomic replacement. External edits, invalid references, duplicate IDs, failed writes and stale editor frames retain the last good catalog and return an actionable error. Manual YAML changes require explicit reload in non-active editing; changing a role never moves players or rewrites their inventories. UI saves may format YAML; comments are not promised to round-trip.

Use a data-only YAML parser, not a handwritten subset or Java object construction. The implementation spike will pin and test SnakeYAML Engine against Java 21/Fabric, preserving its license/notice in the artifact. Reject custom tags, duplicate/recursive keys, aliases/merge keys, multiple documents and environment/file includes. Bound bytes, nesting, nodes and string lengths before conversion. Published [Engine API](https://javadoc.io/doc/org.snakeyaml/snakeyaml-engine/3.1.1/) and [project source](https://github.com/snakeyaml/snakeyaml-engine) are the research references checked on 26 October; no dependency is installed or version locked by this design document.

Initial engineering targets: at most 128 roles, capacity 1–512 consistent with `PlayState.MAX_PARTICIPANTS`, and a kit that fits within 36 normal inventory slots when empty, including split stacks and books. Reuse existing identifier/item-component limits. Final limits require parser/item tests; do not publish unmeasured capacity promises.

### Assignment and lifecycle

- Definitions live under **Advanced → Player Roles**. Actual GM assignment lives under **Players → selected player**. The player sees their own selectable-role chooser; GM-only definitions/private book details are not sent to other players. Roles do not automatically overwrite character cards or expose assignments publicly.
- One current role per account in this campaign. Capacity is derived from assignments, not a second mutable counter. Online and offline assignments reserve seats. Lowering a cap below assigned count, deleting an assigned role and racing for the final seat are rejected. Departed assignments remain historical/reserved until a GM explicitly clears the assignment; clearing a role does not clear departure.
- Self-choice is available before first active entry. GM reassignment can occur during play after confirmation, subject to capacity and no operation hold. Reassignment releases the old seat and updates future policy, without granting another kit, moving the player or resetting first-entry/book receipts. No multiple-character/archive engine is introduced here.
- Definition edits affect future unclaimed starts and future respawns after current validation; in-progress grants pin their exact definition revision. Changes do not replay a completed start. A point edited elsewhere remains stale until deliberately reselected.
- Existing per-player spawn settings are preserved as explicit overrides. Role defaults must be visibly distinguishable from a manual point or explicit Off. Extend effective-policy resolution; do not maintain two independent automatic teleport schedulers. Existing arrival receipts remain authoritative, and resetting a movement receipt never resets a kit grant.
- Offline assignment is limited to known accounts in the campaign/cache; no guessed name-to-UUID lookup or arbitrary unseen roster entry is required in v1. Applying spawn/kit effects waits for a real eligible online player.
- On upgrade, existing participants/arrival histories are marked already started without teleporting or granting items. Assigning a role to an accepted existing player changes future respawn policy only. New campaigns/players receive the first-entry workflow normally.

First entry means **entry into active participation**, not the first meeting, every login, every death or every session start. A new player who chooses a role while play is already active can start on the next eligible check; they do not need to wait for another meeting. Starting items are granted once per account/campaign. Respawn gear is not added implicitly; this request supplies an independent respawn destination.

### Coordinated first entry and private books

Preflight the resolved destination, current player/role/revisions, full item fit and all book definitions before changing anything. Reuse loaded-only safe destination validation: an unloaded, stale or hazardous destination defers entry with a clear remedy; it is not force-loaded or replaced with an invented point. No drops or inventory overwrites when supplies do not fit; keep an unclaimed entitlement pending and explain that room is needed. Existing player inventory/components are preserved.

A single first-entry coordinator owns movement and the kit. Persist the immutable operation and conservative claims before effects; acquire a Core operation hold, then perform the exact planned changes on the server thread, save player data, record actual book discovery and complete receipts. Do not run old arrival movement and a separate role-kit movement independently. Save failures before mutation issue nothing. Any uncertain post-claim result holds the operation for inventory/position inspection; it does not blindly replay or automatically reset a once claim. Recovery can recognize exact saved post-state, but ambiguous outcomes require deliberate GM resolution.

Role books are explicit personal entitlements, not percentage loot rolls. They use fresh Core-managed book provenance and can bypass automatic chest-spawn limits as deliberate GM grants already do. **Receiving the book counts as found**, consistent with the accepted inventory-receipt rule; first finder/time are preserved and any keep request completes. A shared role may give the same named introduction once to each entitled player. Reassignment does not repeat private books. Titles/content/rules stay in Books & Lore; roles store references only. This is a design assumption available for correction during review, not a new separate discovery policy.

## CF21 — paired area states and recoverable world changes

### Area model and navigation

**Player Roles**, **Departures** and **Area changes** are separate Advanced entries in the left navigation. They are not Game setup categories. Area changes presents areas directly, not a template catalog followed by another transition catalog. Game setup retains unrelated existing configuration such as Block limits.

An `AreaChange` references exactly one Core `Region` and its geometry revision, plus independently versioned optional `Start` and `End` snapshots. Creation registers those bounds in the existing Regions registry; the operator does not first create another region or a separate source/target pair. Either state may be captured first. A missing state remains visibly missing; it is never guessed or synthesized. Events and departures reference an area ID and requested state, with an exact captured revision/hash pinned at execution. Only the requested state must be present and current.

Existing Region edits must invalidate stale captures rather than silently crop, resize or stretch them. Region replacement/retirement consults reverse references: refuse while an active capture draft or committed area operation pins its geometry; otherwise atomically mark dependent area captures unusable and retain their exact old geometry/payloads/evidence. Never silently redirect an area to replacement bounds. Retain old payloads for already committed operations. Area changes does not introduce another geometry registry or duplicate map settings under Locations.

### First capture: menu to world to explicit save

1. **Area changes → Create new area** opens one popup asking whether the operator is starting with the Start or End state. Include the area name in the same popup; no extra configuration submenu.
2. Choosing Start or End begins a server-owned, connection-bound `AreaDraft` and closes the editor into world selection. Ordinary RegionDraft and AreaDraft selection are mutually exclusive: refuse to begin an area draft while an ordinary RegionDraft is open, and refuse every ordinary region create/edit entry point while an AreaDraft is active, explaining how to save/cancel the current draft. This exclusion is bidirectional, including commands and menu requests. Preserve the prior ordinary selection/preview, route both position commands to the one active typed draft, and restore that prior state on completion/cancel only if its identity is still current. Another operator has independent selection state; stale shovel packets cannot change either a new area draft or an ordinary region draft. Put a tagged temporary debug shovel in the operator's hand without overwriting/dropping their existing item. A full inventory/hotbar yields a private actionable refusal; command selection remains possible. Do not replace a real shovel or infer tool identity from its display name.
3. Send selection instructions privately to that operator. Left click sets position 1, right click position 2; cancel the shovel's normal mining/use action. Existing `/chronicles author region pos1` and `pos2` (including the singular alias and accepted coordinate forms) set the same draft's corners. Persist the private bounding-box preview through movement until save or cancel.
4. `/chronicle area change save` validates both positions, name, draft identity, geometry and capture prerequisites; then saves the area and chosen snapshot together. It does not apply another state or advance play. A failed save keeps the draft and outline for correction/retry. Provide `/chronicle area change cancel` to leave selection without publishing anything.
5. On save/cancel/disconnect clean up only the token-matching temporary tool and selection state, preserving real inventory items. Never scan/force-load chunks to hunt stashed tools. A stale tool/draft cannot save or resurrect a deleted area.

### Saving current states

After creation, **Save current area state → Start / End** remains available whenever the operator returns to the area. It uses the already saved bounds and offers replacement when that slot exists; no repeat corner selection and no once-only capture restriction. Capture requires operator authority, loaded bounded chunks, matching geometry and no conflicting operation. A read-only capture can run during active play under a temporary operation hold; preserve the previous play phase. Creating/deleting geometry retains the normal non-active Editing guard. These operational prerequisites are not a consumed permission: using/applying an area never removes the recapture action.

Read world data only on the server thread with a per-tick budget. Store relative block positions, a palette of registry states and audited block-entity payloads. Validate capture consistency before publishing the immutable hash. On a failed/partial capture the old saved state remains authoritative, and a new area is not published half-created. A replacement creates a new immutable revision; committed operations retain their pinned payload.

Proposed storage: `world/chronicle/area-changes/` contains an atomic area catalog, immutable snapshot payloads and durable operation/deletion journals. No separate user-facing template store is needed. Never deserialize arbitrary filesystem paths from definitions. Do not copy Core metadata, assignments, managed-instance UUIDs, loot/book transaction markers or ecology ownership into a snapshot.

Initial engineering targets to validate before shipping: 262,144 cells, 512 blocks per axis, 64 intersected chunks, 64 MiB decoded snapshot data, bounded per-block-entity data and at most 128 areas. Reject before allocation rather than truncate. A finite capacity rehearsal must determine practical heap, disk and tick budgets.

Area-state application is intentionally repeatable: each deliberate Start/End application gets a fresh reviewed operation ID and durable before-state. Retrying that same operation remains idempotent. A ship departure retains its own single-use receipt independently. Preserve orientation and the saved area's exact dimensions. No scaling, mirroring, arbitrary schematic imports or entity copying. Initially support audited vanilla containers/signs and explicit project-block adapters. Reject unsupported block entities and unresolved source loot tables by name without rolling loot. Rewrite serialized positions for the same area; normalize container items through existing item/enchantment limits.

Core-managed lore provenance must not be cloned from a capture inventory. Reject it with a direction to use named lore/chest definitions; ordinary written-book content remains ordinary content. Quiet Below's Relic Heart is not cloneable. Station/sculk adapters validate quotas and normalize transient power/vitality without cloning ownership or bypassing Heart protection.

### Applying Start or End

An operator may apply a saved Start or End state during ACTIVE play without Editing. During preparation, explicit non-active Editing permits a reviewed application. The requested snapshot must match the current area bounds; recapture remains available after application. The same execution service is called by departure or a separately configured world-action trigger; there is no hidden paste inside an audio preview.

Preflight all target chunks, dimensions, registry data, current bindings, freshly reviewed execution before-state, quotas and campaign policy. V1 requires the target to be clear of **non-spectator players**; refuse/defer with an actionable message rather than enclosing or dropping players during a partly applied operation. Sinkholes can appear during active play when their area is clear. For ship removal, the already-committed passengers become Spectators before block replacement; any other non-spectator in the footprint prevents departure at preflight. Entities are not copied or relocated by v1.

The final review explicitly states that target blocks, block entities and container contents will be replaced, discarding old contents. Persist a prepared intent and acquire the interaction-blocking operation hold/region reservation before closing affected container viewers. Block container reopen and vanilla inventory mutations under that reservation, close every affected viewer, and revalidate closure before reading raw NBT or taking the before-snapshot. Defer if closure/exclusivity cannot be established; release only this preparation's reservation on a precommit refusal. No close-to-snapshot interaction gap is permitted. Snapshot raw target block-entity NBT, including an unresolved vanilla loot-table ID/seed, without opening or rolling its inventory. Reject partial double chests or other supported multi-block structures crossing the reviewed bounds; do not mutate a neighboring container outside the target. Snapshot their exact before-state and the exact selected-snapshot after-state durably before effects. The world need not currently equal the saved opposite state: the explicit operation authorizes replacement of that reviewed current target; it does not confer permission to overwrite subsequent unexpected edits.

Keep that same single operation hold/region reservation through durable snapshot publication and bounded main-thread writes. Compare each current cell against its planned before/after state before proceeding. A known after-state is an idempotent completion, a known before-state may be applied, and any third state becomes a conflict hold. Receipt/checkpoint progress must not get ahead of durable chunk data. Save/flush affected chunks before completing the operation and releasing its hold. Never restore the entire region blindly on failure. Keep original evidence and an explicit recoverable operation status after interruption.

Capture/apply must not force-load chunks. An unloaded target defers; a real unload during mutation holds progress and awaits normal loading/revalidation. Startup installs holds for committed unfinished operations before gameplay, chest refill or book keeping runs. Validate bad/truncated journals and preserve them, without “repairing” evidence automatically.

### Deleting an area

Delete opens one confirmation offering **Set to Start**, **Set to End**, or **Leave unchanged**, then delete. A missing/stale state cannot be selected, with the reason visible. Leave unchanged removes the area definition without touching terrain. It does not delete an independently used Core Region.

For Start/End, preflight the same supported apply operation and persist a delete intent pinning the selected snapshot before effects. Apply and durably save the requested state before retiring the definition; a refusal/conflict keeps the area and evidence available, never silently falls back to unchanged. Restart preserves the apply-before-retire obligation. Retain operation history/tombstones and referenced payloads rather than erasing recovery evidence or reusing IDs.

Show linked event/departure consumers in the deletion review. Deletion must leave those links explicitly unresolved and execution disabled until reconfigured; a missing area must never be interpreted as no optional link. Pending committed operations block deletion. Publish definition retirement and consumer invalidation together. The ordinary Regions registry keeps a single coherent reference/use list.

### Cross-service integration is part of CF21

These are requirements, not optional post-release cleanup:

- Reconcile replaced/added supplied blocks through managed-instance reservations and confirmed world receipts. Preflight quotas using removals plus additions; failure cannot bypass unloaded-instance limits or free a reservation whose outcome is uncertain.
- Preserve sculk ownership journals through the scenario's normal observed-write hooks. Transitions may not erase/clone the Heart or silently regenerate an eradicated network. Refuse overlap with active ecology maintenance/eradication or another reserved operation. No campaign rules are hardcoded into Core.
- When a target contains a managed lore book, record its pending removal in the shared ledger under the transition operation, then confirm destruction only after durable target save. Keep original discovery history. Book keeping remains held until removal/provenance is resolved, so a crash cannot make a second “kept” copy while the first remains in a chest. This integration must precede enabling arbitrary managed-chest replacement.
- Existing target chest bindings remain explicit metadata and are revalidated against the resulting block; source bindings are never copied. If a container is deliberately removed, its binding retirement is an explicit operation effect with durable receipts. Other map-use/anchor references must remain valid or have an explicitly authorized retirement in the prepared operation; otherwise preflight refuses. The consumed departure may retire its own exact pinned helm consumer after the world receipt, retaining its location/used history. This is not permission to erase unrelated references or bypass managed-block reconciliation. Later ordinary refills use the existing scheduler/loot table, not a second template timer.
- World-change Events use a typed action operation and completion receipt. Existing message/sound cues remain unchanged. Preview outlines the target and describes the change without mutation; completion is recorded only after the world operation succeeds. No default timer, chapter or first-session schedule is registered.

## CF20 — irreversible group departures

### Binding and confirmations

Definitions contain an exact block Anchor, an existing boarding Region, localized first/final text, single-use policy and optional area-change ID and requested Start/End state. Bind a looked-at vanilla block directly in the departure editor, or choose an existing Block site. The shared Locations registry receives the one anchor; it does not acquire duplicate limits/settings menus.

Only occupied ACTIVE, unheld play permits the actual interaction. The actor must be an enrolled, alive, non-departed, non-spectator, non-author participant inside the boarding region, near the exact valid block. The roster uses online eligible participants physically inside that region, including the actor. Game masters are not added merely because they have operator permission. Offline participants and players outside remain behind.

Stage one explains taking the only ship and names the current passengers. Continue opens the separate point-of-no-return dialog above the first. Cancel/Escape on the second returns to the first; underlying controls cannot be clicked or keyboard-activated. Cancel is focused initially. Final text must explain both individual departure and the campaign-ending case. No passenger-by-passenger veto or additional third dialog is added.

Server tokens are connection-bound, expiring, one-use and pin actor, exact passenger UUID set, block/region/configuration revisions, membership revision/predicted campaign-ending consequence and linked area/snapshot revision/hash. Revalidate phase, hold, range, actor, every passenger, roster equality and target preflight at both stages and commit. Any change requires a fresh first review, including a new boarder; do not silently take a different group. Concurrent final clicks resolve at most one operation. A preview cannot execute this flow's durable action. Consume only one main-hand interaction for a bound departure block; do not also open a vanilla container/station UI or open duplicate offers from the off hand. After a committed action changes the actor to Spectator or concludes play, the success response must not be replaced with a fresh ?not eligible? gate error.

### Commit, recovery and ending

Final acceptance first creates one durable departure intent containing the roster, spectator effects, prepared optional area ID/state/snapshot hash and `concludeCampaign` obligation computed from the fully revalidated membership/departure ledger. This is the irreversible boundary. Before that boundary, all linked-transition checks and reservations must succeed. Failure leaves everyone participating and the ship intact. Never let “missing area/state” mean “no linked world change.”

After commitment, one coordinator owns the operation: hold play, persist departed status for the exact roster, suppress participation/automatic respawns/role starts, set Spectator, save player data, apply the staged ship transition, persist the pinned campaign-concluded outcome when required, confirm all receipts, then release only its own hold. The departure cannot become complete or release its hold while that conclusion obligation remains pending. A crash or disconnect after commit cannot undo departure or select new passengers. Effects still pending for a disconnected committed passenger are applied on reconnect before ordinary join/spawn logic. Interrupted/uncertain world changes retain the hold and exact operation; no new departure is permitted.

Membership APIs, `/chronicle join`, role assignment, manual participant toggles and automatic spawns consult durable departed status. Changing a gamemode manually is not permission to re-enroll a departed character. No normal UI reversal is provided; operator repair of corrupted/interrupted data is a separate recovery operation with evidence, not a gameplay “return” button.

After removing the committed passengers, evaluate **all enrolled non-departed participants**, including offline participants. Offline people left aboard were not transported and therefore still prevent an all-departed ending. If none remain, persist a campaign-concluded outcome and close play. `CampaignService.end()` alone is insufficient: it currently permits the next meeting to start. The new durable outcome must also gate start/resume/join/role starts after restart, while leaving non-active operator authoring available. Do not implement permanent game-over by abusing an unresolved-operation hold.

Departure does not destroy the Relic Heart, erase books/inventories, clear Altar receipts or pretend the ecology was eradicated. It ends participation; a whole-group exit concludes this campaign by departure. Introducing a replacement character or resetting a concluded campaign requires separate future design.

## Commands and UI authority

Typed native-menu requests are the primary interface. Suggested fallback groups are role listing/self-choice/GM assignment, area-change selection/save/cancel, state capture, preview/apply/status/recovery and delete-with-state choice, and departure status. Selection reuses `/chronicles author region pos1` and `pos2`; explicit capture uses `/chronicle area change save` (with `/chronicles` alias) and cancel uses the same group. Other fallback spelling follows the approved UI. Registered choices must have server completion; ordinary players are never asked to invent a namespace or filesystem path.

All fallbacks invoke the same services, revision checks, confirmations and operation receipts. A command cannot bypass capacity, give another starting kit, replace an unreviewed region or clear departure/conclusion. `Preview` is read-only presentation; an apply requires explicit confirmation of the exact current plan. Do not expose an undocumented force-success or reset-history action to make tests pass.

## Quiet Below integration (QB14)

The scenario registers its YAML role defaults and its default ship wording/single-use spectator policy. Configure starting/respawn Points and book references through Core. Final named cast, private-character prose and balance remain part of the already deferred content pass; do not repurpose the five ancient-researcher recipe journals as every character's starting lore.

The map builder supplies key geometry only: role Points, ship helm/boarding region and one set of bounds per ship or sinkhole area. Capture the current built scene as Start, prepare its replacement in those same bounds and capture End (or capture End first). Apply Start to restore the prepared scene before play; ship departure requests End. No second source plot or target definition is required. These are explicit finite world changes; no sculk routes, focus blocks or spread painting are introduced. The ecology still discovers its own physical path.

## Independent design review

The read-only architecture review identified three concrete gaps before implementation: active container viewers/raw unresolved target loot, the durable all-departed conclusion obligation, and intentional retirement of the ship's own consumed anchor. This revision incorporates all three, preserving existing receipts and requiring refusal for other unplanned binding changes. The earlier 56-check prototype report belongs to the superseded template/transition design. This paired-state/navigation revision passes its independent design review and 96 Edge prototype assertions with no JavaScript errors; six desktop/compact captures, script syntax, local links and diff checks were reviewed separately in `../reports/area-changes-design/report.json`. Selection isolation, reverse Region references and reservation-before-container-closure are now explicit. The organizer workflow review remains the gate. This is not a claim of installed functionality.
