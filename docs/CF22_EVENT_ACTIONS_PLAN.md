# CF22: unified Events and saved Region changes

27 October 2026. Scope authorized by the organizer: accept dev59 loot-table configuration and dev60 menu feedback/pause/Building Mode; focus on finishing Quiet Below. An Event can combine editable text, an optional sound and one or more saved Region changes. The organizer explicitly wants creation/editing of events, including their text and sound. This document is an implementation contract, not a claim of installed functionality. The live review stays on accepted dev60 until a verified replacement is ready.

## Ownership and scope

Chronicle Core owns event definitions/overrides, editor, trigger configuration, audience selection, bounded action plans, durable execution and recovery. Quiet Below supplies its default messages/sounds and consumes the shared tools. No sinkhole timetable, session narrative boundary, new encounter engine, temporary Altar trade, sculk route or scenario content is inferred. Final writing and handcrafted-map integration remain later gates.

Keep one Events page. Existing supplied events and newly created events use the same editor; do not introduce a second Composite-events catalog or make a message/sound cue another container the organizer must select. Preserve existing cue configurations, elapsed-time credit, manual previews, completion history and explicit flag actions. An upgrade must not arm new events, erase history or leave old and new automatic dispatchers both firing the same event.

## Authoring and triggers

The [dedicated UI design](CF22_EVENT_UI_DESIGN.md) and [interactive mockup](design/events.html) precede native UI implementation. Create belongs above the list. Reuse native popup/widgets and shared searchable, paged selectors. The accepted vertical navigation, clean/debug behavior and compact List/Details flow remain. IDs can be generated on creation and are immutable afterwards. Cancel writes nothing; Save never executes an event.

The definition contains name, optional description, optional player message and optional registered sound. Its configuration contains explicit audience and trigger settings plus an ordered list of saved Region states. Require at least one actual effect: message, sound or Region change. Keep message-only and sound-only events possible. A configured audience is either eligible participants or eligible participants in a selected audience Region. Region-entry triggering selects its own trigger Region; that Region does not implicitly become a world-change target.

Manual, active-time, entry and condition modes reuse the existing participation, occupied ACTIVE clock and condition semantics. Paused, Building, empty and held time never advances these triggers. Optional prerequisites remain explicit. Creating a definition does not start a session or invent a schedule. Mutations require current operator/non-active Editing; live reviewed execution requires a live OP2 player and eligible active play, retaining the existing non-active Editing route for deliberate administrative Area application. The normal event run remains an active-play action. Console use does not acquire a new bypass. Automatic execution uses a narrowly scoped server coordinator with recorded automatic/entry provenance, not an impersonated operator player.

Each change selects an existing Region with Saved states and an explicit Start or End. Pin Region/area revision and immutable snapshot hash when saving/reviewing; independently pin the audience Region and entry-trigger Region revisions. Moving bounds, replacing a state or removing a reference invalidates the old configuration until deliberately repaired. Missing references remain visible. Reject duplicate targets and overlapping inclusive bounds. Initial engineering limits: at most eight targets in one dimension, at most262144 total cells, at most64 unique chunks and64MiB combined retained decoded before-plus-after evidence across the batch; retain existing block-entity/item complexity limits. A streaming implementation must enforce an equivalent explicit memory bound, not count only the after snapshots. These bounds are not story rules. Cross-dimension batches are outside this first slice because the existing aggregate managed-block plan is dimension-scoped.

## Preview and live execution

Private preview may show bounds and play the chosen text/sound to the requesting operator. It performs no terrain changes, completion claims, timer consumption or campaign callbacks. Live Review shows the actual audience and all replacements, including discarded container contents. Recheck the complete pinned plan on confirmation; a stale review never silently targets newly captured states.

Use one same-dimension batch operation. Do not queue N independently prepared Area operations: their chest revisions and managed-block plans would all refer to the original ledger, and the first commit would invalidate the others. Reuse existing capture/write/policy helpers and before/after classification through an explicit batch seam in the Area executor. Preserve existing single-region and departure contracts.

Before reserving or changing terrain, validate the effective event definition, registered sound and exact configured audience/trigger references. Then validate all targets, loaded chunks, player exclusion, exact saved-state/Region pins and campaign policies; capture and verify every before snapshot with a shared tick budget. Prepare one aggregate managed-block quota plan, chest/lore/binding effect plan and exact immutable evidence. Freeze map interactions through a single owned runtime hold. Reserve the shared stores once. A missing, stale, unloaded, overlapping, occupied, quota-invalid or unsupported later target must leave every earlier target unchanged and produce no player media or completion.

Persist a batch UUID, definition/configuration fingerprints, active session/prerequisites, audience, ordered child before/after references, aggregate effect hash and phase/cursor. Apply only from durable intent, in bounded work increments. Child checkpoints are terrain/evidence only: no aggregate managed-block, chest, lore, binding or anchor commit occurs until EVERY child is AFTER, final verification succeeds and one final server world save succeeds. Only then commit the aggregate metadata through idempotent receipts. Resume a committed batch from its exact evidence after restart. Never roll back over foreign edits or create a new operation to retry an uncertain one. Recheck the pinned phase, session and prerequisites at each child boundary and before outcome. An unexpected later edit, player entry, missing chunk or changed phase/prerequisite stops the same batch under a visible hold until its exact recovery requirements are met.

After all terrain and shared effects are verified and durably saved, record the event outcome. Claim media durably before sending its text/sound to the pinned audience, following the existing at-most-once observation policy. A crash around network delivery cannot guarantee exactly-once player receipt; retain explicit uncertainty and never replay the media automatically. Recovery must distinguish unfinished world work, finished-world receipt reconciliation and uncertain media. Resetting an event cannot abandon a pending batch or erase operation evidence. An intentional new run gets a new reviewed operation and replaces the selected states again.

Keep legacy flag-only `CampaignService` handlers pure. World mutations belong to this typed coordinator, not inside an event callback that the campaign service assumes is side-effect-free.

## Durable event authority and restart order

Extend the existing PlayService/PlayStore authority with default/custom definition overrides and a bounded current `EventExecution` map keyed by event ID. Each execution has a fresh operation UUID and immutable plan hash. Its explicit phases are PREPARED, APPLYING, TERRAIN_SAVED, WORLD_COMMITTED, EVENT_OUTCOME, MEDIA_CLAIMED and COMPLETE, with CONFLICT and MEDIA_UNCERTAIN carrying explicit recovery outcomes. Media-only events use the same dispatcher and omit terrain phases. The event outcome and media claim are separate: neither a world save nor a CLAIMED delivery implies that the whole operation finished.

Only the existing trigger scheduler may start executions. It skips every event with a current execution, including complete/uncertain executions, and every preserved legacy delivery receipt until an explicit reset. The progressing batch coordinator is not a second trigger scheduler. Both manual and automatic entry points call the same dispatcher; no old automatic cue-delivery path may remain active for events owned by this dispatcher. Legacy CLAIMED/DELIVERED data remains authoritative and cannot trigger new media on migration. Preserve the old clock/participants and map old bound Regions to their explicit trigger/audience purpose without silently changing scope. The backward-readable PlayStore migration is independently reviewed and tested before deploying it.

Prepare immutable batch evidence before publishing its PREPARED reference in the PlayStore. Missing or mismatched referenced evidence fails closed; orphan immutable files grant no execution authority. Persist phase changes/checkpoints through this single execution owner. Existing Area/managed/content receipts remain subordinate idempotent evidence, never competing event-completion authorities. On a deliberately allowed new run, archive the terminal execution by its UUID before clearing its current pointer/rearming; archive failure retains the old pointer. Pending/conflicting executions cannot be reset or deleted. Operation evidence is never erased to permit a retry.

On startup, load and reconcile executions and recreate their aggregate content/managed reservations and runtime hold BEFORE enabling any automatic event scheduler. This requires explicit registration ordering/readiness guards: current PlayRuntime registration precedes WorldAreaOperations and cannot be assumed safe. A post-world crash resumes only receipt reconciliation or media handling, not terrain application. Loading MEDIA_CLAIMED without durable completion records MEDIA_UNCERTAIN and never resends automatically; the GM can deliberately acknowledge that uncertainty before allowing another run. No physical work remains held solely to pretend that network receipt can be proven.
