# LC-08 Event pools and complication UI design

Status: **workflow approved by the owner on 8 November 2026; native implementation in dev.6, functional review pending**. Interactive prototype: [Event pools and Council complications](../../design/last-council-pools.html). It is self-contained and works as a local file; reset discards all sample state. The review toolbar and the simulated due-condition checkbox are outside the game screen and are not proposed runtime controls. This is a layout and flow mockup, not a scheduler or Event executor.

## Entry points and ownership

- **Core authoring → Events → Event pools:** a reusable pool list on the left and selected pool detail on the right, following the existing editor list/detail and shared picker patterns. Create/name a pool; add existing Events via the searchable picker; select an entry to inspect it, adjust a positive weight, or remove it. A reference is unique within a pool: in particular, a once-only Event cannot be duplicated to bypass once-only behavior. A pool is definitions and references, not a live draw or private world progress. Requirements/bindings remain part of the existing Event definition and validation, not a replacement Event editor.
- **Advanced Game → Council complications:** select an Event pool; set one total across the evening, eligible declared meeting opportunities, arrival window and spacing; see actionable validation. Zero disables complications. The administrative configuration is separate from ordinary Chancellor proceedings and contains no live selection, seed, target, pending allocation, or countdown. Eligibility and feasibility are server-validated, including actual Event requirements, once-only capacity and bindings. Empty/no-eligible pools refuse an enabled configuration or enter explicit recovery; never fabricate content or silently drop a slot.
- **Chancellor proceedings:** ordinary Call meeting, Recess, Resume, request Regency and close meeting remain the relevant procedural controls. Only delivered complication history is added to the workspace; no new political dashboard. Normal players and GM, including Debug, never receive future Event choices, timing, targets, seed or hidden allocation. Authoring may inspect possible source entries without previewing the live draw. The example shows only a delivered Event after the simulated gate.

## Arrival and recovery flow

1. At a safe boundary in an eligible active/unheld Council, the system selects and durably commits a compatible Event and invocation before dispatch through the existing Event executor. An open ordinary ballot is preserved until a safe boundary. A retry/restart must use the committed invocation, not reroll; no future preview is generated by opening a screen.
2. The Chancellor requests Regency. If this meeting has a due obligation, deliver **one** due Event and enter normal Council recess. Core play remains ACTIVE; this is not technical session pause. The Event appears in delivered history only after delivery. No Regency ballot opens.
3. The Chancellor explicitly resumes proceedings and separately requests Regency again. Repeat the gate for another due Event, respecting the reviewed spacing/recess policy. A meeting without Regency has the equivalent gate on meeting close. A later meeting's allocation does not block the current meeting.
4. On changed or cancelled future opportunities, require explicit redistribution and feasibility validation, or an exceptional early-end action with a reason and durable accounting of undelivered obligations. Do not report undelivered as delivered, reveal hidden allocation, or silently discard it. The owner approved confirmation followed by redistribution, with an explicit early-end reason when no future capacity remains.
5. Insufficient eligible entries, interrupted dispatch and technical holds produce actionable recovery without revealing a different future selection or inviting a reroll. Do not advance count before the authoritative invocation completion/acknowledgement. Keep Event occurrence and once-only history intact.

Complications are Events. A letter may be narrative content; a physical book is optional and would require a separate supported delivery extension. No book engine or compulsory item is introduced.

## Approved rules and initial scope

The owner approved two complications across three declared Council meetings, with targets 5-25 occupied active Council minutes after opening and five-minute spacing. All values are configurable. Zero disables the feature. Gathering, time between meetings, technical pauses, Building Mode, empty play and holds do not advance this clock. Discussion and normal Council recess do.

Future meeting cancellation requires confirmation. Undelivered future obligations are redistributed among the retained future opportunities; current/claimed obligations remain fixed. With no future capacity, an explicit early-end reason records obligations as undelivered. It never fabricates completion. Configuration is operator authoring; the Chancellor's normal proceedings expose only delivered history.

The initial pool supports enabled manual once-only Events with no delay. Positive weights affect eligible choices without resetting once-only history. An ordinary ballot is never interrupted. Timed discussion arrivals use the existing Event executor; a forced late arrival at a Regency/meeting-close boundary durably recesses the Council before any ballot/close commits. Explicit resume and a separate request are required. Force never bypasses minimum spacing.

Exact Core invocation completion is required before counting a reveal. Interrupted selections remain pinned and use generic recovery/uncertain-media acknowledgement. Private Region labels and content are omitted even from the Chancellor unless that viewer was a saved recipient.

## Native layout and acceptance

Keep screens small and focused. Reuse native left lists, separately styled read-only description cards, the existing searchable picker and finite actions; wrap full labels and scroll detail at compact sizes instead of hiding content. The prototype stacks columns on narrow viewports for review, not as a pixel-exact native layout. Product controls need server authority checks, bounded projections and stale-frame handling; no hidden data belongs in ordinary/debug packets, exports, or logs.

Review by clicking: create and name a pool; add/remove existing Events, change weights, and empty the pool to see validation; configure zero, opportunities and timing; explore both cancellation requests; switch to proceedings, enable the external due fixture, request Regency or close, observe one delivery and recess, resume, and request again. Also check no future Event, allocation or countdown appears in proceedings. Multiple-due spacing and actual eligibility are contract requirements, not simulated by a client-side random generator.

Before native delivery, verify server-enforced gates through all ballot/close paths, fixed open-ballot state, pause/held and out-of-Council timing, restart/retry idempotence, cancelled/last-meeting accounting, exhausted/once-only pools, privacy in ordinary GM/player/debug packets and logs, and compact/native accessibility. Browser interactions are not evidence of these server properties. Lead review and owner approval of this design precede implementation.


## Lead review refinements

Create pool sits above existing pools and opens a name popup; Add existing Event sits above entries. Explicit Save pool and Save settings controls give feedback. The initial backend supports only once-per-campaign manual zero-delay Events: repeatable source media is shown disabled as future support, preserving its current occurrence restrictions. Changing a field in this layout prototype is draft UI state, not a server-side save. Dynamic browser verification was unavailable in this environment; HTML IDs and JavaScript syntax are checked, while the owner subsequently approved the workflow. Native functional review remains necessary.
