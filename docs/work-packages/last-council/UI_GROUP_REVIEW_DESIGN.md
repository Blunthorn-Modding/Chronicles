# Council group-review native UI design

Status: dedicated UI-agent design reviewed by the lead before implementation on 8 November; implemented in dev.5. Verification is recorded separately in GROUP_REVIEW_VERIFICATION.md. Scope: native Council screens and Advanced Game catalogue; no new overlay, picker, or separate dashboard. This specifies presentation and projection needs, not a new ballot ledger. Feedback: [7 November review](REVIEW_FEEDBACK_2026-11-07.md). Regency clarification received 8 November: retain absolute majority; wait until all remaining candidates are present.

## Existing surfaces and constraints

`CouncilScreen` provides the centred frame, scrollable lists and `SectionCard` stacks; `CouncilBusinessScreen` owns lectern and Chancellor proceedings; `BallotScreen` owns casting; `PersonalScreen` and `HouseSetupScreen` establish existing navigation and setup conventions. The frame is `min(480, width-20)` by `min(360, height-20)`; at 320x240 it is 300x220. The current ballot uses 72-pixel cells, clips names, and puts metadata in one string; compact proceedings currently allocates 84+72 pixels to navigation and list before detail. `ProceedingsPayloads.Detail` has motion fields but no attempts, `View` has active ballot ID but no progress, and `Vote` includes voter UUID/name and a Core `BallotView`. These observations are implementation starting points, not a claim that existing projections suffice.

## Shared presentation

Extend the existing section-card stack with small reusable builders for **Question**, **Proposal**, labelled fields, **Result**, and **Attempt**. Use the same title colour, 10-pixel line spacing, paragraph wrapping, card padding and 4-pixel inter-card gap across screens. A field is a label followed by its value, never a pipe-delimited sentence. Cards are read-only, not black input boxes. Only create a section when it has real content. All wrapped lines are reachable by scrolling, including long unbroken names (break at glyph boundaries if necessary); preserve scroll position and keyboard focus across server pushes, clamp only when content shrinks. Scrolling may be via wheel and visible up/down controls, with keyboard access; do not rely on hover to reveal text.

- Question: motion title, displayed first and wrapped in full. Proposal: description, wrapped in full.
- Fields: **Proposed by:** captured public character name or Chancellor; **Status:** Proposed / On agenda / Vote open / Recorded / Deferred / Withdrawn as appropriate; **Vote type:** Public / Secret; **Decision rule:** plain language. Before opening, say e.g. `Majority of the opening electorate` or `Two thirds of the opening electorate`; do not invent N. Once opened, use the captured numerical threshold and N, e.g. `Majority: 3 of 5 required`. Explain the actual rule from authoritative data, including the applicable Regency absolute majority, not an inferred tally formula. Label sponsors or notes only when present and relevant.
- Result appears only for a closed actual attempt, with its recorded outcome and closed totals where authorized. A proposed/deferred motion without an attempt has no Result or history placeholder. Prior voided attempts remain visible even if the current motion is proposed or deferred.

## Layout and overflow

At normal sizes retain existing left navigation/list and right detail, but guarantee detail >= 180 pixels by sizing the navigation and list from available width. At compact widths (frame < 380), stack in the same screen: a 20-pixel-high motion-list viewport with previous/next selection controls, then a full-width scrollable detail viewport, then pinned action rows. Proceedings navigation uses a compact vertical scrolling area in the same screen above the motion selection, with its own visible scroll affordance; it is not a popup. The details and action buttons never overlap; controls remain accessible even with long content. At 320x240, inner width is 276 (12-pixel side insets); reserve header 34, footer 24, two 20-pixel action rows plus 2-pixel gap where applicable, leaving 120 pixels for navigation, list and detail. Allocate 22 navigation, 22 list, 76 detail; each viewport clips and scrolls independently. Lectern with three actions reserves 64 pixels and gives remaining space to list/detail. Normal layout uses existing scrollable lists/cards, with at least one whole text line visible. Visible arrows indicate additional content and disabled ends; no text is permanently clipped. Motion list labels may be abbreviated in the row only because selection exposes the complete title in the adjacent/below Question card.

Live ballot: after the header, a single vertical scrollable content area holds Question, Proposal, vote type/rule, roster and own choice/eligibility. Pin applicable casting choices at the bottom, with previous/next paging if options exceed available rows; confirmation retains the existing first-choice-is-final semantics. At 320x240 reserve header 34, footer 24, and up to two 20-pixel option rows with 2-pixel gaps; content viewport is at least 118 pixels. One option per page plus navigation is acceptable for long option labels, provided full option text is wrapped and readable before confirming. There is no Refresh button: remove its timeout instruction as well. On timeout say the server did not answer and allow a safe retry/reopen; do not imply a vote was accepted.

Roster: 24-pixel head inside a 26-pixel outline, name centred below and wrapped to the cell width with no fixed line limit. Choose columns from available width with minimum 100-pixel cells; at 276 pixels use two columns of 132 pixels with an 8-pixel gap. Each row height is 30 plus the greatest wrapped name height; position each row with `rowLeft = viewportLeft + (viewportWidth - (count*cellWidth + (count-1)*gap))/2`, including the last partial row. Centre heads and names within cells. Scroll the content rather than truncate names or require hover. A pathological name longer than the viewport remains readable by scrolling the complete wrapped name. Public outlines remain neutral/green/red/amber for not cast/For/Against/Abstain; provide a textual legend so colour is not the sole cue. Secret outlines and tooltips stay neutral with no submission state. On the live screen omit duplicate named For/Against groups; show the voter's own final choice when authorized. A closed/reopened ballot may show its actual closed result; void shows its public reason without inventing a result.

## Contexts and history

Lectern motion selection displays Question, Proposal, fields, and actual attempts in chronological order in the same scrollable detail stack. Each attempt identifies its order, status (open / closed / void), vote type, captured rule and, if void, public reason. Closed public attempts show recorded outcome and named **For**, **Against**, **Abstain**, and **Not cast** groups when applicable, using names captured at opening, not current House labels. Lists wrap and scroll; empty groups may be omitted. Open attempts are clearly open and must not be presented as results. Secret attempts reveal no named choice or per-person turnout, including in void history; closed secret attempts show aggregate results only. Replacement attempts are distinct and previous attempts/reasons remain visible. No live controls appear at the lectern.

Proceedings uses the same Question, Proposal and field builders for the active motion. Its active-ballot section shows progress directly, without opening the voter screen: `3 of 5 votes submitted`, or `All 5 votes submitted`. Public progress additionally lists captured outstanding character names, wrapping fully; an abstention counts as submitted and disconnects remain outstanding. Secret progress provides only anonymous count and N, never individual flags, names of outstanding voters, ordering or timestamps. Completion does not close the ballot or alter threshold. Existing Close and Void controls remain pinned. Server pushes update progress and eligibility without reinitializing focused inputs, opening screens, flicker, or changing selection.

## Regency and setup

Regency candidate labels are public character names with their associated House as secondary text; candidates and frozen voters are distinct. Retain absolute majority. Before opening in later meetings, require all remaining eligible candidates to be present: if any are absent, show the Chancellor an in-place readable refusal naming absent eligible characters and their Houses; keep the full remaining slate unchanged and do not open a partial-slate ballot. Presence cannot eliminate or withdraw a candidate. Once open, candidate choices and electorate stay frozen. Use existing authority and validation at the server, not client-only disabling.

In Advanced Game setup, add a read-only **Source catalogue** entry alongside existing scenario content navigation. Show searchable/scrollable categories House information, secrets, House goals and known-other-House information; select an entry in a left list and show its full source text and relevant source relationships in the existing read-only section style. At 320x240 stack the list and detail as above; full content scrolls. This is administrative access only, not player-facing papers. It shows reusable definitions, never live draws, seeds, assigned papers or who knows a House's secrets. Editing/export remains LC-01B/C planned scope, with no disabled controls implying it already works.

In House setup, distinguish `Papers issued` from a blocked assignment. For an unassigned player, provide an explicit late-assignment entry point and preview/confirmation of the player and available House, with text that existing papers and prior ballots remain unchanged; the exact safe draw/publication design is separate and must be settled before enabling the action. An already assigned player or occupied House has an explicit, specific refusal rather than being treated as the same operation. Never imply reassignment or takeover is supported until designed. Do not expose the catalogue or another player's papers through Personal screens.

## Projection and update contract

Use Core's immutable ballot history as the authoritative source; Council only navigates/project it. Add bounded, purpose-built fields as needed: per-motion attempts with stable ballot ID, sequence, status, captured title/rule/threshold/N, public void reason and closed result; for public attempts, captured character identity/name and choice or not-cast; for secret attempts, aggregates only. Do not send raw ledger/votes. Existing `History` (ID/title/status) and `Detail` cannot express this. For Chancellor proceedings add a separate authority-checked progress projection containing ballot ID, submitted count and frozen electorate N; only public progress may include captured outstanding identities/names. Secret progress must not be encoded in ordinary `View`, `Vote`, reusable exports, or any per-person field. Recheck authority on every subscription push and reconnect; revoke or clear stale privileged state on loss of office. Existing `Vote.voters` can support heads, but public history needs captured character names reliably associated with the immutable attempt, not a lookup against today's House membership. Restrict and bound all added lists/strings and fail closed on malformed/stale data.

Retain automatic changed-projection updates (existing ten-tick subscription cadence) for ballot and add equivalent authorized proceedings updates. Preserve ballot ID/revision and opening/request guards; update only the active subscribed screen and do not steal focus. Close/void, own confirmation, eligibility, public outlines and Chancellor progress must propagate; reconnect and reopen reconstruct from authoritative state.

## Review and acceptance

- At normal size and 320x240, test one, partial-row and many voters, short and maximum supported long names, long unbroken names, multiple attempts and long proposal/reason text. Every name and field is reachable without hover; heads are centred per row, controls never overlap, and keyboard/wheel scrolling works.
- Unvoted motion has no result/history; a voided attempt stays visible after replacement; closed public history groups captured names including abstained/not-cast; secret history never exposes individual turnout or choices. Restart and reopen preserve attempts.
- Public and secret live ballots update automatically without Refresh; choice confirmation, eligibility and close/void updates survive reconnect. Test authority transfer: only the current Chancellor receives secret aggregate progress; ordinary packets, exports and tooltips contain no secret per-person or aggregate turnout. Verify stale privilege is cleared.
- Frozen electorate controls N and outstanding public names despite late arrival, departure or disconnect; abstention is submitted, all-submitted does not auto-close. Test open and closed/void attempts separately.
- With an absent remaining Regency candidate, Chancellor sees their name/House and cannot open a partial slate; once all are present the full slate opens with absolute majority, frozen thereafter. Preserve prior ballots and slate through restart.
- Inspect catalogue under authorized Advanced setup and verify ordinary players cannot fetch assignments or knowledge links. Test late-assignment cues separately from actual safe draw implementation; no reroll, historical rewrite or occupied-House takeover is implied.
- Lead review of this document precedes implementation. Native hosted-LAN multiplayer, packet/privacy checks and compact screen review remain required; this document itself is not evidence those checks passed.
