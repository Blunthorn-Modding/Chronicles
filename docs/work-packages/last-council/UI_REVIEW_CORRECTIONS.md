## Observed gap

The scene prototype already uses a visible left motion list with a separate right detail, and a visible left list for Other houses. The native `CouncilBusinessScreen` instead puts `Choose motion...` above one long `ScrollableTextWidget`, and combines procedural actions and the selected motion. Its lectern mode additionally offers operator-only Prepare, Admit and Proceedings controls. `PersonalScreen` uses a picker for Other houses and concatenates all public information into one text widget. `CouncilScreen.body` uses a `ScrollableTextWidget` for every read-only body; this produces the large dark input-like panel rejected in review. `BallotScreen` similarly puts descriptions, named votes and totals into a long text widget. The existing prototype's Chancellor scene itself uses a motion dropdown, so this review explicitly supersedes that part of the prototype. Its example operator/Chancellor assumption is also superseded by the assignment rule below.

## Shared native geometry and presentation

Use the existing Chronicle popup frame, buttons, font, focus conventions and character card rather than designing a new visual language. Targets: normal viewport at least 500×380, centered frame **480×360**; compact viewport **320×240**, centered frame **300×220** with 10 px outer margin. Frame header 28 px, footer 24 px, inner horizontal margins 10 px, column gap 6 px, 20 px buttons and 2–4 px spacing. Reserve feedback in the footer without covering controls. Do not rely on viewport-relative overflow; scissor and scroll each long region independently, preserve selection and offset on server refresh, and show a visible scrollbar or clear scroll affordance. Text wraps and never clips or overlaps controls. If the viewport becomes narrower than the compact target, allow a vertically scrolling frame while preserving both list and details, rather than replacing the list with a picker.

Normal two-column content width 460: left **142**, right **312**. Compact content width 280: left **98**, right **176**. Within the right column use 6 px internal padding. These are minimum planning measurements, not a claim of tested rendering. Selected rows need a persistent border/background and a non-color selection cue; long names truncate with full text available on hover/focus. Rows expose accessible labels, keyboard navigation, and mouse wheel scrolling. Empty, loading, unavailable and server error states have readable plain text. Buttons remain keyboard accessible and disabled actions explain their reason.

Use actual text fields only for editable input: character-card editing, motion title/description, required defer/void reason and search where useful. A field must have an editable affordance and focus behavior. Render read-only prose as wrapped text and separately labeled, lightly differentiated sections on the frame surface; scrolling may use a transparent/clipped scroll region, not a black textbox. Use selected rows and labeled cards/separators for visual hierarchy. Reuse `DossierScreen` for the existing character editor and existing confirmation/reason/draft patterns where suitable; share a small scrollable row-list and read-only detail renderer across these scenes, not a new universal dashboard.

## Motion lectern

World interaction with the bound lectern opens the list directly. Normal frame: header, then list at x+10/y+32, width 142, height 274; right detail x+158, width 312. Compact: list x+10/y+32, width 98, height 142; right x+114, width 176. List rows show motion title and status, scroll in place and retain selection. The right pane has selected title, a separately styled **Description** section and **Details** section (proposer, status, visibility, threshold, sponsors and applicable notes), then eligible player actions. Scroll the detail independently; reserve its action row or make it reachable within the pane. Place Propose in the footer or a stable top action and Sponsor/Withdraw against the selected motion when authorized. Keep recorded-ballot access only if it remains part of the player workflow, clearly separate from selected-motion controls.

The lectern contains **no Chancellor procedural controls**, including Prepare, Admit, Open vote, Regency or Proceedings, regardless of operator status. Server projections remain the authority for proposal/sponsorship/withdrawal eligibility and physical lectern context. Stale selection or access loss must produce an actionable response without silently operating on another motion.

## Proceedings

Provide a separately rebindable **Open council proceedings** key and corresponding existing command path, scoped to the explicitly assigned Chancellor. The key follows existing ballot access safeguards for workstations, text entry, editor discard and delayed responses. It does not turn the lectern into a shortcut to authority. Compact Chronicle-style left navigation/actions and a right workspace replace the current single summary and button stack.

Normal: within the 480×360 frame, navigation x+10/y+32, 142 wide, workspace x+158/y+32, 312 wide, height 294. Compact: within 300×220, navigation x+10/y+32, 98 wide, workspace x+114/y+32, 176 wide, height 154. Navigation scrolls if needed; preserve access to the bottom actions. Order: Call meeting, Open meeting or Resume/Recess as applicable, Prepare motion, Motions, recorded/active ballot as applicable, **Regency immediately above Close meeting at the bottom**. Recovery appears only when relevant. Call remains available during an open vote and recess when permitted. The right workspace presents phase, selected navigation content and concise feedback; do not conceal a disabled action's reason.

Motions workspace uses a visible list and selected detail with **Open vote** and **Defer** together on the selected item; show Admit where the server requires it. In the normal workspace reserve 104 px for rows, 6 px gap and 202 px for detail. In the 176 px compact workspace use 70 px rows, 4 px gap and 102 px detail, with independent vertical scroll and full-title tooltip. Buttons may stack in the narrow detail. Prepare opens the existing draft flow; Regency is a directly gated sidebar action with confirmation, rather than another workspace. While any ballot is open, its own motion details and View/Close/Void remain available; choosing another motion cannot hide those controls. Void requires a public reason. Confirm destructive/final actions and preserve request/revision guards.

All pending motions must be resolved by a completed vote or explicit defer before Regency becomes available. Enforce this on the **server**, including stale requests and alternate command paths; the client merely displays disabled state and a short reason. Define pending from authoritative meeting state, including submitted and admitted motions, without treating withdrawal or a voided ballot as a completed vote. If a void leaves the motion unresolved it must be voted again or deferred. Keep the existing due-complication/recess and once-per-meeting succession constraints in addition to this gate. The exact status-to-pending mapping and migration of already-open meetings require implementation review against persisted state.

## Personal menu

Retain the clear Character / My house / Other houses tabs. Character uses existing card information and `DossierScreen` to edit it. My house keeps House information, Secrets, Goals and Other houses' secrets as distinct selected sections, each shown once, with only the recipient's authorized papers. On compact sizes use a scrollable left section list as space permits rather than an input-like text body.

Other houses uses the shared normal 142/312 and compact 98/176 list/detail split. The visible left house list is independently scrollable. The right pane shows the selected name, then separately labeled public Reputation, House information, Interests and Representative/candidacy sections, each rendered as read-only text. No private facts, goals, reports or editable-looking black panel. Keep a clear empty state when no other house exists and retain the selected house through refresh when still present.

## Ballot

At the top, show the captured electorate as player heads, using vanilla player-list/Tab head and skin rendering conventions and the character-card name under each head. Lay out tiles in wrapping rows, scrolling the roster if necessary; use 72 px-wide tiles at normal and compact sizes (24 px vanilla head plus character label), paging the roster when needed, with a clipped single-line name and full name on focus/hover. Roster identity is the frozen electorate at opening, not the live online list; disconnected voters remain represented. Default or unavailable skins use the standard fallback without revealing an extra identity. If the existing projection does not supply a safe stable skin identity and character-card label for each captured voter, add an explicitly authorized projection/snapshot and test it; do not infer character names from account names or fetch private data. Multiple representatives per house need an authoritative representative snapshot rather than a guessed player.

Public ballot heads start with a gray border; once a public choice is accepted show green for Yes, red for No and neutral amber for Abstain. Include a text/icon cue or accessible label for each state, so color is not the only signal. For options outside Yes/No/Abstain, use a neutral border and a readable public choice label; never mislabel a candidate as Yes/No. Secret ballot heads **always remain neutral**, including after close. Do not disclose turnout, individual votes or vote-state changes before close; after close show aggregate totals only, without attributing choices to heads. These restrictions apply to every recipient, including the Chancellor, and must be enforced by server projections, not simply hidden in rendering.

Below the roster show only title, concise description, visibility and required threshold, then choice buttons and the voter's own final choice/status. Keep warning/error copy when needed; confirmation says the first accepted choice is final. Closing is not abstention. At compact size prioritize the roster, title and choices; scroll overflow rather than shrinking text or covering buttons. Continue to honor frozen electorate, current Region eligibility, immutable choices, delayed responses, and the existing access/return behavior.

## Assignment and authority

Chancellor is an explicit, separately configured assignment, confirmed by an operator through the administrative setup flow. A player cannot simultaneously hold a house assignment and the Chancellor assignment; validate this server-side on assignment, reassignment, load and relevant mutations, with a clear conflict message and no silent removal of either role. Operator privilege alone grants no Chancellor status and does not prevent an operator from playing a house. Administrative setup is separate from the Chancellor's proceedings UI. Confirm exact setup placement and migration/error handling during implementation; do not assume an existing operator flag expresses this assignment.
