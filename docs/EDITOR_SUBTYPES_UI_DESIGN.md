# Region and Location subtypes: editor design

**Status: design proposal for organizer review.** This revises the approved CF19–CF21 editor organization; it does not authorize implementation or change the current runtime. The [interactive mockup](design/editor-subtypes.html) illustrates the proposed screens, not Minecraft behavior.

## Navigation and shared rules

Keep the native Chronicle three-pane layout and familiar buttons. Advanced retains Regions, Locations and Player Roles; remove the standalone Area changes and Departures destinations. Create appears above the relevant list, never inside selected details. Ordinary Regions remain generic geometry. A Region has zero or more independent, nonexclusive subtypes; a subtype picker uses checkboxes and applies a deliberate change. A Location has a subtype picker, with Departure controls shown only when Departure is selected. Other consumers select a Region in their own editor; Region details do not have a reverse “Use for” assignment.

With Debug off, show descriptions and controls needed for the task; Debug on additionally shows IDs, revisions, bounds and operation diagnostics. Compact layouts drill into one pane at a time. Keep existing permission, phase and operation-hold guards from the approved design.

## Regions and saved states

Region details provide name, description, subtype selection, selection/bounds editing, and **Preview bounding box**. A Region without Saved states shows no capture or application controls. Enabling Saved states exposes Start and End independently: capture current blocks into either state, apply either available current state, and delete the subtype with a deliberate choice to apply Start, apply End, or leave terrain unchanged. Explain replacement of blocks and container contents on apply, list affected consumers before deletion, and retain failure/hold/occupancy safeguards and history from the approved design. Save/capture/application failures retain the prior valid data. The existing in-world selection and command workflow remains available.

Changing selection bounds must never silently rebind saved snapshots. Before committing changed bounds, warn that both snapshots become stale and identify affected consumers. Require explicit confirmation; stale states cannot apply or satisfy a departure until separately recaptured for the new bounds. A committed operation or pinned draft blocks the bounds change. If a safe atomic transition cannot be guaranteed, refuse the change and preserve the prior bounds and snapshots. Removing Saved states similarly does not silently turn an existing chosen departure state into “Leave unchanged”: the dependent configuration is unresolved until deliberately repaired.

## Locations and departures

Create Location above the list, including the existing save-my-position creation workflow. Do not duplicate it in selected details. The selected Location stays concise with description, subtype and **Configure departure?**. That button opens one Departure setup popup containing the bound block context, editable multiline first and final warnings, one boarding Region, and the optional state of that same Region. Save commits the popup draft; Cancel discards it. A used departure is immutable. When that Region has Saved states, label the field **After departure, the Region should be:** with **Leave unchanged**, **Start**, and **End**. Start/End are unavailable when absent or stale. If the Region has no Saved states, hide the state selector and leave terrain unchanged. If a previously selected state becomes missing/stale or the subtype is removed, preserve the reference as unresolved and block departure; never silently reset it. There is no second Area selector.

Confirmed by the organizer on 27 October: preserve exact bound-block interaction, such as the helm, with its subtype settings under Locations. Do not add proximity activation. Points remain position/facing records; the Departure capability must explicitly retain a bound physical control rather than converting a spawn Point or silently moving it. Warning text is edited directly in the setup popup; merely opening or editing it never starts a departure. A used departure remains immutable. The live flow preserves the online eligible aboard roster, two stacked confirmations with Cancel initially focused and the underlying dialog inert, final revalidation, exact reviewed passengers becoming departed Spectators, and durable campaign conclusion only when no enrolled non-departed account remains, including offline accounts. Apply the chosen saved state only after the existing full preflight. Offline and ashore accounts stay behind.

## Role starting supplies

The role editor retains explicit modes for Details (name, public description, player-selectable status and capacity), Starting supplies, Lore books, Starting Point and Respawn Point. Switching modes retains the entire unsaved role draft. Existing point and book selection, role validation and save/discard workflows remain available. The mockup represents these sections with sample controls.

The selected role shows its **Assigned starting supplies** list with one row per item, quantity and remove action. **Add item…** opens a separate searchable catalog of **Available items**; selecting an item and quantity adds it to the role draft. Already assigned items are identified, not offered as a duplicate row; change their quantity in the assigned list. Removing an item affects the draft, and saving/discarding the parent role continues to govern all changes. Keep existing role capacity, point, book, eligibility, grant and reassignment semantics. Preserve item components and separately configured variants; never collapse enchanted/custom stacks merely because they share a base item ID.

## Preservation and implementation gate

This is a presentation/authoring reorganization, not a new geometry registry. Existing Core Region identities, references and bounds must be preserved; area capture/application operation histories and departure operation histories, receipts and used status must not change or be reset. Migration must preserve unresolved references and be idempotent; never replay an operation, grant, or departure. Any mapping of the old separate area record to a Region subtype requires explicit compatibility handling, including old departures whose boarding Region and area Region differ; do not silently discard or remap either reference. Such mismatches need an explicit organizer repair choice before a departure can be configured under the single-Region model.

The revised mockup is awaiting the organizer's layout review before structural UI implementation. Existing mismatched boarding/state Regions remain visibly unresolved until deliberately repaired; no separate reset or data deletion is needed. The mockup uses local sample data and does not persist, issue items, alter worlds, or prove runtime recovery.

## Implementation boundaries

Core owns the extensible subtype registry and authoring presentation. Subtypes are independent capabilities, not exclusive replacements for the Region/Point/Block-site geometry kind. Scenario mods can register relevant labels and controls through Core; the current built-ins are Region saved states and Location departure. Store no second set of region coordinates. Existing area IDs and payloads remain internal stable authorities linked to their Core Region; they are not renamed or replayed to achieve the new navigation. Existing commands remain compatibility aliases to the same guarded services. The state choice in a Departure is always for the selected boarding Region, not a separately chosen source area. Missing/unavailable/stale selections remain visible until repaired.
