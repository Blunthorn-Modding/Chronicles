# CF23 Event editor UI design

Status: dedicated design reviewed by the lead before implementation. The organizer authorized implementation and selected the Event-centric flow in `EVENT_FLAG_PROGRESSION_PLAN.md`. This document specifies the native layout; verification and delivery are recorded in [implementation notes](CF23_IMPLEMENTATION.md).

## Structure and geometry

Keep `EventEditorScreen` as one local draft, with five navigable sections in this order: **Basics → When → Requirements → Delay → What happens**. Basics contains the existing name, generated/editable ID on creation, and organizer description. The other four headings are the organizer's logical flow. Do not create separate Media, Region Changes, or Flags modes. Each section is reachable without discarding fields; no completion of an earlier section is required to visit a later section.

Use the existing centered popup dimensions: `w = min(440, max(240, width - 24))`, `x = (width - w)/2`, `y = max(6, (height - 240)/2 + 6)`. At logical 320×240 this yields 296 px content width and y=8; at 640×360 it yields 440 px and y=60. Retain 18 px native buttons, 22 px row pitch, and the 240 px background. A compact section bar at y+22 has a 26 px **<**, a central section name and position (e.g. `Requirements 3/5`), and a 26 px **>**. Tooltips identify previous/next section; disable the endpoint arrow with a reason. This avoids five clipped tabs and gives identical behavior at both sizes. Place description/help at y+46, content at y+60 through y+177, feedback at y+190, and Cancel/Create or Save at y+206. Existing input labels above fields consume 10 px; don't place list rows over labels or feedback. Long text must be trimmed by rendered width with full value/reason in tooltip, not a fixed character count.

For the lists use a fixed viewport with up to four 18 px rows at y+84, +106, +128, +150 and small ↑/↓ controls on the header line. Clamp offsets after removals and section switches; expose earlier/later controls and their disabled reasons, preserve the offset while returning from a picker. Mouse wheel may supplement, never replace, buttons. Both long list and long picker pages must remain reachable at compact size. Picker search, page navigation, row scrolling, Add and Cancel are the existing `CatalogAddPopup` behavior.

## Controls by section

- **Basics:** existing ID/name/description widgets and ID-generation behavior. On edit show immutable ID as existing. Retain the actual text while navigating, including invalid or unfinished text.
- **When:** a full-width `Trigger: …` button opens a labelled choice of registered supported sources, using a paged shared picker when there are more than a handful; the selected source's target and activity use separate full-width picker buttons below. Examples: Manual; Region entry → Region; block activity → managed Location/registered source and explicit supported activity; Book found → book; Book opened → book; departure completion → departure. Show only supported options supplied by the provider/catalog and never require an arbitrary ID or command. Found and opened must have distinct labels. For departure, expose the plan's ended-play behavior in help/tooltip: a matched silent progress Event may finish after play ends; a mixed Event waiting to start is skipped. If no source or target is available show the reason and a route to create it in its normal editor. Changing source must not silently repurpose an incompatible target; keep the previous draft available until an intentional selection, and clear incompatible selection with visible feedback when switching.
- **Requirements:** caption `All required flags must be On` and `Add prerequisite…` opening the shared flag picker. Rows show flag label/ID plus **Remove**; duplicates are disabled in the picker with `Already required`. Zero rows means no flag gate. Missing or stale references stay visible as unavailable and can be removed/replaced; never drop them during decoding. The condition trigger's existing requirement for at least one flag remains visible when applicable.
- **Delay:** an explicit `No delay` / `Active-play delay` choice and labelled active-seconds input when enabled. Explain in concise text or tooltip: time starts only after eligibility and all required flags are On; any required flag turning Off resets the full countdown. Pauses preserve time while flags remain On. Preserve unfinished input when toggling or changing sections; only Save validates a positive supported value. Present only combinations supported by the implementation rather than promising delayed discrete-source behavior the server does not support.
- **What happens:** one list, `Add action…` above rows and no category switch. The add choice offers **Update flag**, **Send text**, **Play sound**, **Apply Region Saved state**; choosing a type opens its small draft editor, or inserts an editable draft row, without sending effects. Rows summarize type and target/value with **Edit** and **Remove** (compact widths: summary w−100, two 48 px controls). Status/tooltip explains unresolved targets. Use the same list for all types, including flag-only Events. Show no ordering affordance unless ordering is a supported semantic; this list is an authoring summary, not an arbitrary workflow. Server-defined execution checkpoints remain authoritative.

Action editing uses an internal mode of the existing native screen, retaining the same parent and local-draft conventions. **Update flag:** shared flag picker and On/Off choice. **Send text:** message text field and participant/selected Region audience, with Region picker if selected. **Play sound:** shared sound picker and same audience controls. **Apply Region Saved state:** shared saved-state picker showing Region + Start/End and pinned revision; retain `Show bounds` for current targets. Preserve existing aggregate media/audience constraints if the implementation retains one message, one sound and one shared audience; disable duplicate or incompatible choices with an explanation rather than imply unsupported multiplicity. Similarly reject duplicate flag targets or Region targets according to server rules and show the reason. Action editor **Done** changes the local draft only; **Cancel** restores its previous value. Full Event Cancel discards the entire draft.

Provide **Preview privately** within the action list or media action editor whenever media exists. It previews unsaved text/sound only to the organizer, never executes flags, terrain, triggers or Event completion. If no media exists, disable it with `Add text or sound to preview`. Preview should not reject an unrelated unfinished delay; preserve its input. The server still validates preview authority.

## Authority, validation, and ownership

`EventEditorScreen` owns transient section, input, list offset and child-editor state. `CatalogAddPopup` owns catalog paging/search and selection presentation, while its owner validates duplicates and applies selection only to the local draft. `EventEditorForm` and its codec represent the supported draft and pinned references, including unresolved entries; `CoreEventMenu` supplies labels, server-generated catalog entries, disabled reasons, and final server validation. `CoreMenuScreen` retains parent/navigation and transport routing. Do not put authority in a client callback or silently substitute a changed revision.

Every mutation, Save, and preview must respect existing opening token/operator/editable/editing/hold checks. When stale, preserve the draft for inspection, mark any open picker stale, disable mutations and preview/save with a visible reason, and leave Cancel/Close available. Rejected non-stale saves retain all input and show the server reason. On success return through the existing parent route; delayed replies must not reopen a closed screen. Save validates missing trigger/targets, duplicate/unavailable pins, action presence and supported combinations, with actionable messages; flag-only is valid. Saving never fires actions. Existing Game Events / Region Changes filters remain; flag updates do not introduce a new category. Advanced → Flags remains saved facts and manual override, not an automation editor.

## Design verification for implementation

At 320×240 and 640×360 inspect each section, action editor and picker with long labels, enough entries to require scrolling/paging, and disabled-reason tooltips; ensure all widgets are within the background and never overlap feedback/footer. Exercise multiple prerequisites, duplicates/removal and stale targets, mixed action types and flag-only save, text/sound preview, empty/invalid delay, picker Cancel and section changes with unsaved fields. Test a stale reply while a child picker is open, retained draft, close/late reply, server rejection, existing edit/create and parent return. Verify book found/opened labels and source/activity selectors reflect actual registered support. This is a UI proposal, not a claim of gameplay, schema, or runtime validation.
